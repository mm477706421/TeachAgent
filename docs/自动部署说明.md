# GitHub Actions 自动部署

正式服务：http://43.165.169.59:8080/ 。工作流为 `.github/workflows/ci.yml`。

## 触发与验证

- 推送到 `main` 后，自动运行后端测试、前端构建、真实服务浏览器测试和 Pages 演示测试。
- 所有验证通过后，`deploy-server` 将本次测试过的服务构建包经 SSH 上传到服务器，并部署该提交；Pages 演示同时独立发布。
- Pull Request 只验证，不部署服务器。也可在 GitHub Actions 中选择此工作流，对 `main` 手动执行 Run workflow。
- 工作流和服务器文件锁串行化部署；失败时查看 `deploy-server` 的日志。重跑工作流会创建独立的发布目录。
- `/api/health` 的 `revision` 为完整 Git 提交 SHA，可以与 Actions 的提交核对。

## 凭据与服务器

仓库 Actions Secrets 配置了以下变量，值不进入源码或构建包：

| Secret | 用途 |
| --- | --- |
| `TEACHAGENT_SSH_HOST` | SSH 服务器地址 |
| `TEACHAGENT_SSH_USER` | 部署用户 ubuntu |
| `TEACHAGENT_SSH_PRIVATE_KEY` | 专用 Ed25519 部署私钥 |
| `TEACHAGENT_SSH_HOST_FINGERPRINT` | 已核验的服务器 SHA256 主机指纹 |

使用 SSH 22 端口；部署用户须具备当前服务器上的免密 sudo 权限。CI 不使用登录密码。服务器主机密钥发生变化时，先独立核验再更新指纹 Secret，不能跳过校验。

服务器已安装对应公钥，并配置 systemd 使用 `/opt/teachagent/current/.venv/bin/python`。Nginx 8080 代理到本机 18080；发布维护标记存在时返回 503 和 Retry-After，健康检查仍可访问。

## 发布与数据保护

1. 校验构建包 SHA256，解压到 `/opt/teachagent/releases/<提交>-<运行ID>-<尝试次数>`。
2. 按 requirements.txt 哈希选择依赖环境。依赖变更时先创建新环境，避免破坏旧版本；检查依赖、应用导入和空数据库初始化。
3. 进入短暂维护状态，等待现有连接、视频上传、分析和对话任务完成。最多等 10 分钟，超时取消发布并恢复访问，不强制中断正在处理的课堂。
4. 停止服务，使用 SQLite 备份接口保存数据库，同时保存环境配置。备份位于 `/opt/teachagent/backups/<提交>-<运行ID>-<尝试次数>`，仅受限账号可读。
5. 原子切换 current，启动新版本，核验本机后端和 8080 健康状态、提交版本，以及已有业务数据指纹。
6. 验证通过才解除维护。此前失败会恢复旧数据库、代码和依赖环境；恢复失败则保留维护状态，避免向用户暴露异常服务。

学校文件仍在 `/var/lib/teachagent`；`/etc/teachagent.env` 中的模型与供应商配置保持原样；模型目录沿用原服务器配置。仓库与 Actions 构建包不包含学校数据。

## 运维与恢复

- 查看状态：`sudo systemctl status teachagent nginx`，`sudo journalctl -u teachagent -n 100`。
- 查看当前版本：`cat /opt/teachagent/current/DEPLOYED_REVISION`。
- 若自动恢复失败，先检查日志、磁盘和备份，保持 `/opt/teachagent/deploy-maintenance` 存在；确认旧版本、数据库、依赖和服务健康后再删除该标记。不要直接删除标记来绕过错误。
- 自动数据库恢复只在本次发布尚未开放访问时执行。新版本已经接收写入后，不应直接恢复旧快照，否则会丢失新数据。历史 `deploy/rollback.sh` 不属于此自动发布流程。
- 已有业务字段发生变化的迁移会被保护检查拒绝。需要数据转换的升级应单独设计迁移和恢复方案；当前自动流程支持不改动既有数据的增量结构变更。
- 快照仅备份数据库和环境配置，视频文件仍需学校常规备份。发布目录、依赖环境和快照不会自动清理，应定期检查磁盘，保留当前和需要回滚的版本。
